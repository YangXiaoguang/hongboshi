# 运营管理后台建设路线图

## 目标

红博士后续会逐步成为一个带有课程商品、咨询服务、用户权益、订单交易、支付退款、财务核算和风险复核的心理服务交易平台。运营管理后台不是简单的页面集合，而是承载业务状态机、权限、审计、对账和人工处理流程的稳定系统。

本路线图用于指导 Codex 持续二次开发：每个阶段都要能独立交付、可测试、可回滚，并且为后续阶段留下清晰的扩展点。

## 当前基础

已完成或具备基础能力：

- 前端使用 React、TypeScript、Vite、Tailwind CSS。
- 后端使用 Express 模块化 API。
- `shared/domain` 已承载前后端共享 Zod 契约。
- 已建立 `visitor`、`member`、`counselor`、`operator`、`admin` 角色和 `admin:manage`、`counseling:fulfill` 等权限能力。
- 咨询运营配置页面 `/admin/counseling` 已可管理取消规则并查看履约审计。
- 支付对账页面 `/admin/payments` 已可对比支付回调收据、业务订单和咨询预约状态。
- 课程商品列表 `/admin/courses` 已接入统一后台，可读取课程商品契约、搜索、状态筛选、分类筛选、排序、分页、基础信息编辑、详情内容编辑、内容质量校验、审核动作、上下架、改价和最近审计；状态与详情内容均可写入 JSON Store 或 PostgreSQL，并已联动前台课程列表/详情。
- 咨询预约、支付回调、风险事件、测评结果、课程权益等模块已开始使用 Store 接口，并具备 PostgreSQL 实现或迁移基础。

主要缺口：

- 课程商品当前仍缺少更细粒度权限和素材真实文件管理，内容运营闭环还需要继续收口。
- 订单、交易、退款、财务账务还没有统一后台视图和状态机操作入口。
- 用户管理、会员管理、风控审核、审计中心还没有形成独立模块。
- 权限仍偏粗，需要从 `admin:manage` 逐步演进到资源级和动作级权限。

## 建设原则

- 共享契约优先：跨前后端的数据结构先进入 `shared/domain`，再由 client 和 server 消费。
- 服务端掌控状态：订单、支付、退款、咨询预约、财务和风险流转由 server service 决策，前端只提交意图。
- Store 抽象稳定：每个核心领域先定义 Store 接口，再提供内存/JSON/PostgreSQL 实现，API 不直接绑定数据库细节。
- 权限和审计内建：后台读写接口必须校验角色/权限；敏感操作必须记录操作者、对象、动作、前后状态和时间。
- 页面只做呈现：筛选、排序、状态推导、异常判断优先放在 feature repository 或 server service。
- 小步可交付：每个阶段都要有测试、文档更新、CI 验证、Git 提交和推送。

## M1: 统一后台框架

目标：把已存在的 `/admin/counseling` 和 `/admin/payments` 纳入统一后台体验，为后续课程、用户、订单、财务模块建立稳定骨架。

交付内容：

- 新增 `client/src/pages/admin/AdminLayout.tsx`，提供后台侧边导航、顶部上下文、权限提示和内容区域。
- 新增 `client/src/pages/admin/AdminHome.tsx`，展示后台模块入口、关键风险提示和当前建设状态。
- 新增后台导航配置，统一声明模块 key、标题、路径、权限和状态。
- 保留现有 URL：`/admin/counseling`、`/admin/payments` 继续可访问，但使用统一布局。
- `AppHeader` 中的运营入口指向 `/admin`，再由后台内导航进入具体模块。
- 增加前端测试覆盖后台鉴权、导航和现有页面接入。
- 更新 README、产品工程路线和本执行状态文件。

验收标准：

- 未登录用户访问 `/admin` 能看到登录提示。
- 非运营/管理员用户访问 `/admin` 能看到权限不足提示。
- `operator` 或 `admin` 用户可进入后台首页，并能导航到咨询运营和支付对账。
- 现有咨询运营、支付对账页面功能不回退。
- `pnpm run ci` 通过。

## M2: 课程商品管理

目标：把课程从展示型 seed 数据升级为可运营的课程商品。

交付内容：

- `shared/domain/courseProduct.ts` 定义课程商品、分类、价格、状态、审核状态和列表查询契约。
- `server/modules/catalog` 建立课程商品 Store 和后台 API，支持从课程 seed 初始化商品快照，并可用 JSON Store 或 PostgreSQL 持久化。
- 后台课程商品列表 `/admin/courses` 支持搜索、分类、状态筛选、排序和分页。
- 课程商品支持基础信息编辑、详情内容编辑、审核动作、价格编辑、上下架动作和审计记录。
- 前台课程读取已从课程商品 Store 读取 `published + approved` 商品，并同步价格和会员权益。
- 下一步补齐课程商品更细粒度权限和素材真实文件管理入口。

验收标准：

- 运营可在后台看到课程商品清单并执行上下架。
- 前台只展示已审核通过且已上架课程。
- 价格和状态变更有审计记录。

当前状态：

- M2-A 已完成：共享契约、只读 API、前端 repository、后台列表和导航接入。
- M2-B 已完成：新增服务端写动作、价格编辑、上下架规则和课程商品审计事件。
- M2-C 已完成：课程商品 JSON Store、前台发布状态过滤和价格联动。
- M2-D 已完成：课程商品 PostgreSQL Store、基础信息编辑、数据库迁移和审计事件。
- M2-E 已完成：课程商品审核状态流、审核动作 API、驳回原因展示和详情内容契约。
- M2-F 已完成：课程详情内容 JSON Store、后台内容编辑、前台详情内容读取和复审保护。
- M2-G 已完成：课程详情内容 PostgreSQL Store、批量内容校验、审核提交前校验和后台校验状态。
- M2-H 下一步：课程商品权限细化与素材管理收口。

## M3: 用户与会员管理

目标：建立客服和运营可用的用户管理入口，同时保护心理服务隐私边界。

交付内容：

- 用户列表、搜索、角色/会员状态筛选。
- 用户详情聚合基础资料、会员权益、课程权益、订单摘要、咨询预约摘要和风险提示。
- 敏感字段最小化展示，并为查看敏感信息预留更高权限。
- 会员开通、到期、权益调整走服务端动作和审计。

验收标准：

- 运营可以按手机号、昵称、用户 ID 检索用户。
- 用户详情不直接暴露咨询记录全文和测评答案。
- 会员权益调整可追溯。

## M4: 订单管理

目标：把课程订单、咨询预约订单和会员订单纳入统一订单管理。

交付内容：

- 统一订单领域契约，区分商品类型、金额、优惠、支付状态、履约状态和退款状态。
- 后台订单列表、详情、筛选和状态时间线。
- 订单状态机动作：关闭待支付、标记异常、查看支付/退款关联。
- 课程权益、咨询预约和会员权益都通过订单状态驱动。

验收标准：

- 订单详情可以解释当前状态来自哪个支付或业务事件。
- 订单状态变更不会绕过服务端状态机。
- 关键动作有权限校验和审计。

## M5: 交易与退款管理

目标：建立支付流水、退款流水和异常处理入口，为真实支付渠道接入打基础。

交付内容：

- 支付渠道适配接口，支持微信、支付宝或模拟渠道逐步替换。
- 交易流水列表和详情，关联订单、回调收据和业务对象。
- 退款申请、退款回调、退款异常处理动作。
- 支付对账异常从只读提示升级为可处理工单。

验收标准：

- 每笔交易都能追溯到订单和业务对象。
- 重复回调、金额不一致、业务状态不一致能够被标记并处理。
- 退款动作不会直接修改业务状态，必须通过回调或受控模拟事件完成闭环。

## M6: 财务管理

目标：让运营和财务可以查看收入、退款和实收基础数据。

交付内容：

- 财务看板：收入、退款、净收入、待处理异常。
- 按日期、商品类型、支付渠道聚合统计。
- CSV 导出基础能力。
- 财务口径文档化：下单金额、支付金额、退款金额、实收金额、手续费预留。

验收标准：

- 财务统计来自交易/订单领域，不从页面临时计算。
- 导出字段稳定，并带有生成时间和筛选条件。
- 数据口径在文档中明确。

## M7: 咨询运营增强

目标：把咨询业务从预约闭环升级到可运营的服务管理。

交付内容：

- 咨询师排班管理。
- 咨询师资质和服务状态管理。
- 履约异常、未到访、改期、取消原因统计。
- 取消规则版本化和灰度配置预留。

验收标准：

- 咨询师服务能力可以被运营配置。
- 排班变更和规则变更可追溯。
- 已有关联预约的时段不能被危险修改。

## M8: 风险复核台

目标：承接心理测评和咨询前信息中的高风险信号。

交付内容：

- 风险事件列表、详情、来源和等级。
- 人工复核动作：标记已联系、建议咨询、升级处理、关闭。
- 风险 SOP 文案和处理结果模板。
- 与用户详情、咨询预约、测评报告建立受控关联。

验收标准：

- 高风险事件不会只停留在日志里。
- 复核动作有处理人、处理时间和结果。
- 敏感内容按权限展示。

## M9: 审计中心

目标：建立跨模块操作追踪能力。

交付内容：

- 统一审计事件契约和 Store。
- 后台审计列表支持按操作者、对象、模块、动作、时间筛选。
- 关键模块逐步接入统一审计。
- 导出和事件详情基础能力。

验收标准：

- 敏感后台动作都能在审计中心追踪。
- 审计事件不可被普通后台操作修改。
- 审计查询性能有基础索引设计。

## 每阶段固定交付清单

- 更新或新增 `shared/domain` 契约。
- 增加 server service、API、Store 接口和必要 PostgreSQL 迁移。
- 增加 frontend repository、页面、状态和错误处理。
- 增加权限校验、审计事件和异常提示。
- 增加单元测试或集成测试。
- 更新相关 docs 和 `docs/codex-execution-state.md`。
- 运行 `pnpm run ci`。
- 提交 Git commit 并推送到 GitHub。
